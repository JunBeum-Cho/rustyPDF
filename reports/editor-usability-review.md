# RustyPDF 편집기 사용성 개선 및 후속 검토

검토일: 2026-10-21. Electron 전환 작업을 유지하면서 승인된 일곱 가지 사용성 개선을 적용했다. 새 런타임 의존성은 추가하지 않았다. 기존 Rust/Tauri 소스 삭제 상태도 유지했다.

## 적용한 개선

| 항목 | 바뀐 동작 |
|---|---|
| 실행 취소 / 다시 실행 | 주석 편집과 페이지 삭제·복제·붙여넣기·잘라내기·회전을 사용자 작업 순서로 되돌린다. 삭제한 페이지의 편집 가능한 주석과 그 이전 주석 기록도 복원한다. 저장 뒤 되돌리면 다시 변경 상태가 된다. |
| 비동기 편집 보호 | 실행 취소 응답을 기다리는 중 새 주석이 생기면 새 주석을 유지하고 페이지 상태를 원래대로 돌린다. 일시적 복구 실패는 재시도하고, 복구 전에는 다음 저장·페이지 편집이 진행되지 않도록 했다. |
| 저장 의미 구분 | 저장, 다른 이름으로 저장, 주석 포함 PDF 내보내기를 구분했다. 편집 데이터 보관과 공유용 PDF의 차이를 도움말·상태에 반영했다. |
| 페이지와 확대 | 페이지 번호와 확대율을 직접 입력한다. 잘못된 입력은 거절하고 유효한 범위로 제한한다. 너비 맞춤·페이지 맞춤은 창/사이드바/페이지 크기 변화에 따라 다시 계산하며 수동 확대는 맞춤 모드를 해제한다. |
| 검색 | 툴바에 검색 진입점을 표시한다. 첫 Enter는 첫 결과로 이동하고, 다음 Enter/Shift+Enter로 순회한다. 결과 위치를 강조하고 화면으로 이동한다. 검색어·탭·문서 변경과 검색창 닫기에 따라 오래된 강조를 없앤다. OCR 완료 시 같은 검색어도 갱신한다. |
| OCR | 기본 실행 범위는 현재 페이지다. 메뉴에서 문서 전체를 선택할 수 있다. 중지, 페이지별 실패 표시, 해당 페이지 재시도를 제공한다. 중지는 다음 페이지 예약과 늦은 결과 반영을 막는다. 이미 실행 중인 인식 작업 자체는 완료될 수 있다. |
| 툴바와 피드백 | 헤더 메뉴 배치는 사용자의 후속 요청에 따라 기존처럼 도구 설정을 이어 배치하는 구성으로 복원했다. 플로팅 텍스트 메뉴의 모션은 유지한다. 다른 이름으로 저장과 맞춤은 작은 아이콘으로 표시하고, Mac/Windows 단축키 표기를 구분하고 입력 요소에서 도구 단축키가 오작동하지 않도록 했다. 페이지·썸네일 렌더링에는 재시도, 복사·페이지 편집·이미지·저장 오류에는 보이는 피드백을 제공한다. |

기존 개선인 OCR 일반 텍스트 복사, 흰색/투명한 외부 텍스트의 검은 글자 붙여넣기, 빠른 텍스트 색상 변경, 확대율을 반영한 글자 크기, 플로팅 메뉴 모션과 동작 줄이기 설정도 유지했다.

실행 취소의 PDF 스냅샷은 문서당 최대 20개와 64MiB 한도로 보관한다. 큰 문서에서는 오래된 기록이 더 빨리 제외될 수 있으며, 제외된 기록을 선택 가능한 상태로 남겨두지 않고 안내한다. 복구 중에는 바로 전 활성 PDF의 참조를 최대 한 개 추가로 잠시 유지한다. 바이트를 복사하지 않으며 복원 확정·롤백·문서 닫기에 해제한다. 보관 기록이 메모리 한도로 정리되더라도 진행 중인 복구는 가능하게 했다.

## 검증

- 최종 소스 기준 전체 자동 테스트: **68 통과 / 실패 0 / 건너뜀 0**. Node 22에서 실행했다.
- 프로덕션 빌드 및 TypeScript 검사 통과. Vite 단계 2.60초. 이 수치는 에셋 준비와 패키징을 포함한 전체 소요 시간이 아니다.
- `git diff --check` 통과.
- 실제 Electron 창: 주석이 있는 페이지 삭제 → 실행 취소 → 이전 주석 실행 취소 → 다시 실행, 회전 취소, 저장 후 다시 실행의 변경 상태를 확인했다.
- 실제 Electron 창: 페이지 직접 입력과 잘못된 입력, 페이지 맞춤 경계, 수동 확대의 맞춤 해제, 첫 Enter 검색, 한 페이지의 여러 결과, 회전된 페이지 결과와 스크롤, 검색창 닫기/재열기를 확인했다.
- 실제 Electron 창: 렌더링 실패를 주입하고 같은 페이지의 재시도 복구를 확인했다.
- 실제 Electron 창: OCR 호출 경계에 실패·지연 응답을 주입해 현재 페이지만 실행, 해당 페이지 재시도, OCR 완료 뒤 같은 검색어 갱신, 전체 인식 중지와 늦은 결과 폐기를 확인했다. 이 검증은 OCR 제어 흐름 검사이며 인식 정확도 측정은 아니다.
- 앞선 실제 창 검사에서 100%·200% 확대 붙여넣기, 검은 글자/굵기 보존, 텍스트 편집 유지, 플로팅 메뉴 중간 프레임과 layout shift 0, 동작 줄이기 적용을 확인했다.
- 720px / 1280px 창에서 툴바 버튼과 입력 요소의 가로 넘침 0. 복원한 헤더에서도 높이는 각각 169px / 103px였다. OCR 옵션 메뉴도 두 크기에서 화면 좌우 여백 안에 표시되는지 확인했다.
- Mac arm64 앱 패키지와 패키지 안의 실제 오프라인 OCR·PDF 렌더링·회전·저장·내보내기 smoke 검증이 통과했다. 헤더 복원 후 최종 소스로 다시 패키징했고, 패키지 실행 검사도 통과했다.
- Windows 단축키 표기는 테스트했지만 Windows 네이티브 앱 실행은 이 Mac 환경에서 검증하지 못했다.

## 다시 검토한 결과: 다음 개선 우선순위

### 1. 화면에서 고른 글꼴과 내보낸 PDF의 글꼴 일치 — 높음 · 후속 작업 적용

**2026-10-21 검토 당시:** 글꼴 캐시가 굵기만 구분하고, PDF 출력에서 텍스트 조각의 글꼴 이름을 반영하지 않았다. 글자 폭 차이가 줄바꿈·정렬 차이로 이어질 수 있었다.

**권장 수정:** Windows와 Mac에서 동일하게 제공할 소수의 글꼴을 정하고 화면과 내보내기가 같은 폰트를 사용하도록 연결한다. 지원하지 않는 폰트는 미리 대체 글꼴을 알린다. 글꼴 이름만 많이 노출하기보다 화면과 출력의 일치를 우선한다. 글꼴별 한글/영문/굵기/줄바꿈 비교 PDF로 확인한다.

**2026-10-22 반영:** 내장 Noto Sans KR / Noto Serif KR의 Regular·Bold 파일을 화면과 PDF가 함께 사용하도록 변경했다. 기존 글꼴 이름은 두 계열 중 하나로 일관되게 대체한다. 후속 검증과 제약은 [팔레트·PDF 출력 보고서](palette-pdf-export-review.md)에 기록한다.

### 2. OCR 결과를 다른 PDF 뷰어에서도 검색 가능하게 내보내기 — 높음 · 후속 작업 적용

**2026-10-21 검토 당시:** OCR 결과를 `.ocr.json` 보조 파일에 보관하고 PDF 내보내기에 OCR 텍스트 레이어를 넣지 않았다. 앱 안에서 인식한 스캔 문서도 내보낸 PDF에는 검색용 텍스트가 생기지 않았다.

**권장 수정:** ‘검색 가능한 PDF’ 내보내기를 추가하고 OCR 좌표에 투명 텍스트 레이어를 넣는다. 먼저 기본 언어와 회전된 스캔에 한정해 다른 뷰어의 검색·복사까지 확인한다. 기존 주석 포함 PDF와 목적을 설명하는 것이 좋다.

**2026-10-22 반영:** 기존 내보내기에 인식이 완료된 페이지의 OCR을 실제 PDF Invisible 텍스트 레이어로 포함한다. 추가 메뉴나 자동 OCR 실행은 넣지 않았다. 후속 검증과 제약은 [팔레트·PDF 출력 보고서](palette-pdf-export-review.md)에 기록한다.

### 3. 재실행 후 마지막 읽던 위치 복원 — 중간

**소스에서 확인한 현재 동작:** `src/viewer/PdfViewer.tsx`의 스크롤 맵은 메모리에 있고, `src/welcome/recentFiles.ts:9`의 최근 파일 정보에는 경로·이름·열었던 시간만 있다. 실행 중 탭 이동 복원은 제공하지만 앱을 종료한 뒤 같은 문서의 읽던 위치를 영속 보관하는 모델은 없다.

**권장 수정:** 파일별 마지막 페이지·확대율·맞춤 모드만 먼저 저장한다. 문서 페이지 수가 바뀌면 범위를 보정한다. 정밀한 픽셀 위치 복원이나 복잡한 세션 관리 없이도 사용자가 매번 페이지를 다시 찾는 일을 줄일 수 있다.

### 4. 이미지 → PDF 목록에 실제 미리보기와 쉬운 순서 변경 — 중간

**소스에서 확인한 현재 동작:** `src/images/ImageImportDialog.tsx:59`는 파일명과 공통 아이콘, 위/아래 이동 버튼을 표시한다. 비슷한 파일명을 가진 스캔 여러 장은 내용과 순서를 확인하기 어렵다.

**권장 수정:** 작은 썸네일과 페이지 번호를 표시하고 드래그로 순서를 바꾸되 기존 위/아래 버튼도 유지한다. 현재의 A4·비율 유지·10mm 기본값은 그대로 두고, 필요한 경우에만 페이지별 회전 정도를 노출한다.

### 5. 키보드 동선과 작은 화면 점검 — 중간

**후속 요청 반영:** 사용자가 새 헤더 구성보다 이전 구성을 선호해 헤더의 강제 행 분리와 고정 빈 설정 영역을 없애고 이전 배치 방식으로 복원했다. 최종 720px/1280px 높이는 169px/103px로, 좁은 창에서 자연스럽게 줄바꿈한다. 이 배치를 유지하면서 키보드 사용성과 화면 가장자리 처리를 개선할 수 있다.

**권장 수정:** 추가 메뉴 재설계보다 썸네일 컨텍스트 메뉴의 화면 가장자리 위치 보정과 키보드 이동, 사이드바 크기 조절 핸들의 키보드 접근도 함께 점검한다. 가장자리 잘림은 소스상 위험을 확인한 단계로, 이번 실제 창 검사에서 재현한 결함으로 단정하지 않는다.

### 6. 반복 빌드의 오프라인 에셋 준비 캐시 — 중간

**소스에서 확인한 현재 동작:** `scripts/prepare-assets.mjs`는 실행할 때마다 PDF.js 리소스, OCR 학습 데이터·런타임, 글꼴을 복사하고 OCR worker를 번들링한다. 변경되지 않은 에셋에도 반복 작업이 발생한다.

**권장 수정:** 먼저 에셋 준비·TypeScript·Vite·패키징을 따로 측정한다. 에셋 준비가 유의미하면 패키지 버전과 글꼴 변경을 기록하는 작은 stamp로 변경 없는 복사를 건너뛴다. 캐시를 지우면 완전히 재생성되는 단순한 방식이면 충분하다. 현재 Vite 단계 수치만으로 전체 빌드의 병목을 단정하지 않는다.

### 7. 검색 강조의 글자 단위 정밀도 — 낮음~중간

**소스에서 확인한 현재 동작:** `src/search/model.ts:44`는 검색 위치를 줄 안의 문자 수 비율로 나눈다. 결과 페이지와 해당 줄로 이동하고 회전 좌표를 처리하지만, 글자마다 폭이 다른 문장에서 검색어 강조의 좌우 경계는 근사치다.

**권장 수정:** PDF.js 텍스트 항목의 실제 폭과 가능하면 글자 위치를 사용하고, OCR은 단어 단위 박스를 유지한다. 새 검색 엔진을 도입할 필요는 없다. 영문 `iii/WWW`, 한글·영문 혼합, 여러 줄 검색에서 경계를 비교한다.

## 성능 관련 판단을 보류한 부분

긴 문서에서는 모든 페이지 프레임이 DOM에 존재하지만 캔버스와 썸네일은 화면 주변에서 지연 렌더링한다. 500페이지 문서의 메모리·스크롤 지연은 이번에 측정하지 않았다. 그래서 지금 가상 목록이나 새 상태 관리 계층을 추가할 근거는 부족하다. 실제 긴 문서를 기준으로 측정하고 문제가 있는 구간만 고치는 편이 원래의 ‘최대한 간단하게’라는 방향에 맞다.

앞의 두 항목은 2026-10-22 후속 작업에 반영했다. 다음 사용성 개선은 **마지막 읽던 위치 복원 → 이미지 가져오기 미리보기·순서 변경 → 키보드 동선** 순으로 진행하는 것이 좋다. 반복 빌드 에셋 준비는 단계별 시간을 측정한 뒤 캐시의 필요성을 판단한다.
